# 升级备份与恢复安全方案（仅设计，未实现）

## 现状与风险证据

- `cmd/server/main.go` 先 `database.Open` / `database.Migrate`，随后才打开凭据密钥、启动服务与后台任务，最后监听 HTTP。健康检查失败不代表数据库没变，也不代表新版本没有产生业务写入。
- `internal/database/migrations.go:Migrate` 每个版本单独事务提交；第 N 个迁移失败会保留前 N−1 个成功迁移。目前没有程序读写 schema 兼容范围预检。
- `internal/updater/helper.go:RunHelper` 的 `restore` 只恢复旧可执行文件并重启，不恢复数据库。不能把现有 `rolled_back` 文案解读为数据已回到升级前。
- SQLite 使用 WAL；单独复制正在写入的 `.db` 不构成一致性备份。v73 历史图片直接存储在数据库，备份同时包含用户私人观看信息和图片。

本轮只形成方案，不改变更新器，不新增恢复 API，不运行真实备份/恢复或覆盖生产数据库。

## 拟议升级顺序

1. 验证官方资产签名/校验和、目标平台、磁盘余量与程序读写 schema 范围。兼容声明缺失时，不提供自动回退保证。
2. 进入维护模式，拒绝新写请求，停止调度、worker、watcher、插件写入，等待当前事务和文件操作到达安全点。拿不到排他维护锁则中止，不强制终止文件移动。
3. 用 SQLite backup API 创建一致性数据库快照；首次实现优先停写后备份。备份必须可在隔离数据库执行 `integrity_check` 与 `foreign_key_check`。禁止裸复制运行中的主库并忽略 WAL。
4. 记录匹配的密钥身份、配置、插件状态和版本。快照封装完成、校验与落盘成功后，才允许替换程序。
5. 候选程序在维护模式先执行兼容检查/迁移/核心服务自检，不运行自动扫描、下载、插件任务。验证完成后才解除停写并接流量。
6. 明确记录升级是否已开放业务写入；升级成功通知只能在自检与接流量状态提交后发送。

## 备份 manifest v1（拟议合同）

| 字段 | 含义与约束 |
| --- | --- |
| format_version, backup_id, created_at | 固定格式版本、随机标识、UTC 时间 |
| application_version, build_hash, platform | 原程序身份；不是用户可覆盖的 URL |
| schema_versions, min_reader, min_writer, max_writer | 实际应用迁移集合及经过测试的兼容范围；未知不能当兼容 |
| database_digest, database_size, snapshot_method | 数据库完整性、大小、一致性快照方法；不保留绝对路径 |
| config_digest, plugin_manifest_digest | 匹配配置和插件版本/权限/状态清单；可恢复配置放加密内容，不放公开 manifest |
| credential_key_id, key_source | 密钥身份和来源类型，不是主密钥或可直接解密的内容 |
| write_fence, resumed_writes_at | 排他维护状态及允许新写入的时间；不得仅依赖健康状态推断 |
| files, archive_digest | 白名单相对路径、大小、校验和，拒绝路径穿越、绝对路径、符号链接和重复文件 |

`credentials.key` 默认位于数据库目录；也可能使用 `OMC_CREDENTIAL_MASTER_KEY`。必须验证实际使用的密钥，不凭文件名判断匹配。使用高熵密钥身份/HMAC 验证哨兵，绝不在日志/清单输出密钥。环境主密钥默认不导出；恢复需管理员提供匹配密钥。允许导出密钥时必须另行明确授权并加密封装。

备份档案按秘密管理：管理员读取、短期授权下载、no-store、审计且不记录内容；服务器本地限制 ACL，下载/离机备份必须认证加密，包含完整性验证。保留策略不能删除最后一份已经验证可恢复的升级前快照。恢复前先验证全档案大小与解包边界，禁止执行其中的插件代码。

## 失败决策矩阵

| 失败阶段/状态 | 可执行策略 | 禁止动作 |
| --- | --- | --- |
| 下载、校验、维护锁或备份失败，尚未替换 | 保留原程序与数据，解除可安全解除的维护状态，报告失败 | 把半份备份标记可恢复 |
| 候选未启动、schema 未变 | 校验旧程序后恢复程序；确认原数据仍匹配 | 覆盖数据库 |
| 部分迁移已提交，尚未放行业务写入 | 若旧程序明确兼容当前 schema，可仅回退程序；否则保留维护状态并要求选择前向修复或显式恢复 | 认为单次迁移失败会回滚全部版本；盲启旧程序 |
| 健康失败，是否发生新写入未知 | 按“可能有新写入”处理，先保留故障现场；明确提示程序回退与数据恢复是两件事 | 自动恢复升级前数据 |
| 已放行业务且产生新写入 | 优先前向修复；需要恢复时展示快照时间、当前时间、历史/收藏/任务等可能损失范围并要求明确确认 | 以修复健康状态为由静默丢弃新写入 |
| 密钥不匹配、校验失败、插件/配置缺项 | 拒绝恢复；原库不动，指出缺失组件，不输出秘密 | 生成新密钥然后假装旧凭据可解密 |
| 恢复候选验证失败 | 保留原程序/数据库/备份，维护模式下诊断 | 覆盖原库后才做完整性检查 |

## 显式恢复流程与权限

未来恢复入口需独立高风险权限、管理员再认证、Cookie + CSRF、防重放操作令牌和审计；普通媒体库/下载管理权限不包含恢复。此处是拟议权限，不声称已有对应 API。

管理员先选择快照，系统只读预检并展示缺失项与数据损失窗口。再次确认后停写、停后台、持有维护锁；将当前数据库作为可恢复的故障现场保留，不删除。将目标快照恢复到隔离候选目录，验证密钥解密哨兵、数据库完整性、迁移兼容范围、配置/插件绑定，插件保持禁用。只有全部通过才原子切换受控数据路径。旧连接全部关闭，撤销恢复前会话/设备凭据的策略必须在实施设计中明确，防止备份让已撤销令牌复活。

数据库恢复不能撤销真实文件移动、115 回收、已提交下载或媒体服务器通知。恢复后暂停这些自动化，先与外部事实对账并复核幂等键，禁止直接重放恢复出来的旧任务。用户媒体文件与外部服务数据不在本备份范围内，界面必须明示。

## 隔离演练与验收（后续实施前必备）

- 使用专用临时根、随机端口、假 Provider；禁止真实账号凭据和生产媒体目录。
- 对迁移前/中/后、自检前后、允许新写入后分别注入失败；验证决策矩阵，而不只测 HTTP 200。
- 验证 WAL 中已提交记录进入快照、未提交事务不进入；多次迁移失败保留准确 schema 集合。
- 备份后增加历史/收藏/通知 receipt，故障恢复必须提示损失窗口，未经确认不得消失。
- 错密钥、损坏档案、目录穿越、缺插件/配置、空间不足、中途掉电均不能破坏原库。
- 恢复已撤销会话/设备以及执行过的文件移动任务，证明不会复活权限或重放外部副作用。
- 保存 RPO（可损失写入时间窗口）与 RTO（实际恢复时间）的实测值；没有演练结果不宣称无损恢复。

结论：当前“程序备份/健康失败回退”已存在，“一致性备份/数据恢复”仍是未实施能力。本方案完整覆盖 R10 的设计交付，不以文档替代恢复功能。
